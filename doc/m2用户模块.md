# 模块 M2 接口契约：用户模块

## 1. 目标（一句话）
用户能注册、登录，拿到 JWT 访问受保护接口（后面所有模块都要用它鉴权）。

## 2. 目录增量（M1 基础上新增）
app/
├── db.py                    # engine + SessionLocal + get_db 依赖
├── models/
│   └── user.py              # User 模型
├── schemas/
│   └── user.py              # UserCreate / UserOut / Token
├── core/
│   └── security.py          # bcrypt 哈希 + JWT 签发/校验
└── api/v1/
    └── users.py             # register / login / me 三个路由

## 3. 数据模型
users 表：
- id: int, PK, 自增
- email: varchar(255), unique, not null
- password_hash: varchar(255), not null   # 只存 bcrypt 哈希
- created_at: datetime, default now()

## 4. API 契约
POST /api/v1/users/register
  请求: {"email": "...", "password": "..."}
  响应 201: {"user_id": 1, "email": "..."}
  错误: 400 邮箱格式错/密码过短 / 409 邮箱已注册
按顺序：
  接请求：拿到 email 和 password
  校验格式：email 是不是合法邮箱？password 够不够长？
  查重：email 是否已经存在？
  哈希密码：不能存明文
  插入数据库：拿到新 id
  返回响应：201 + user_id + email

POST /api/v1/users/login
  请求: {"email": "...", "password": "..."}
  响应 200: {"access_token": "eyJ...", "token_type": "bearer"}
  错误: 401 邮箱或密码错误
按顺序：
  接请求：email + password
  查用户：按 email 查库
  验证密码：verify_password
  签发 token：create_token(user.id)
  返回响应：200 + access_token + token_type

GET /api/v1/users/me        # 需 Authorization: Bearer <token>
  响应 200: {"user_id": 1, "email": "..."}
  错误: 401 token 缺失/无效/过期
按顺序：
  从请求头拿 token：Authorization: Bearer eyJ...
  解析 token：decode_token(token) → user_id
  查用户：按 user_id 查库
  返回：{"user_id": ..., "email": ...}

```bash
# 3. 密码太短 → 422（MVP 阶段可接受）

  -H "Content-Type: application/json" \
  -d '{"email": "c@d.com", "password": "123"}'
# HTTP/1.1 422 Unprocessable Entity
```

热身题目
① SQLAlchemy 建模
   定义 User 模型（对照契约第 3 节）+ engine + SessionLocal
   验证：create_all 建表，插入一行再查回来

② 密码哈希
   hash_password(pw) / verify_password(pw, hash)
   验证：hash 结果不含明文，verify 对错密码返回 False

③ JWT 签发/校验
   create_token(user_id) / decode_token(token)
   验证：能解出 user_id；篡改 token 抛错

④ 注册路由
   EmailStr + password min_length=8 校验；插入库；重复邮箱 → 409
   验证：curl 三次分别拿到 201 / 400 / 409

⑤ 登录路由
   查库 → verify_password → 签发 token
   验证：错密码 401，对密码返回 token

⑥ 受保护接口
   GET /users/me：从 Authorization: Bearer 解析 token
   验证：无 token 401，有 token 返回用户
```bash
    # ① 注册，登录拿 token
    curl -X POST http://127.0.0.1:8000/api/v1/users/register \
      -H "Content-Type:application/json" \
      -d '{"email":"a@bgg.com","password":"password"}'
      
    curl -X POST http://127.0.0.1:8000/api/v1/users/login \
      -H "Content-Type: application/json" \
      -d '{"email":"a@b.com","password":"password"}'
    # ② 带上 token 访问 /me
    curl -i http://127.0.0.1:8000/api/v1/users/me \
      -H "Authorization: Bearer <上一步返回的access_token>"
```

## 1. 30 秒回顾入口（3 个月后看这个就够了）
一句话：M2 = 「让系统认识你是谁」——注册把邮箱+密码变成一条 users 记录（密码只存 bcrypt 哈希），登录把密码换成一张 JWT 凭证，/me 用凭证换回你的身份。

## 2. 逐文件点评（重点：每个文件"为什么这么写"）

### app/core/security.py —— 密码与凭证的加工厂
- 为什么 bcrypt：慢哈希 + 自动加盐，抗彩虹表/暴力破解；sha256/md5 是快哈希，攻击者每秒能算几亿次
- 为什么 JWT 带 iat/exp：过期时间是 JWT 的安全边界，不设过期=永久钥匙
- ⚠️ 问题：这里抛了 `HTTPException`（HTTP 层概念混进了纯工具层）→ 导致 test_jwt 无法直接测"过期"，也让这个函数无法在后台任务等非 HTTP 场景复用。改进方向：security.py 只抛 `jwt.PyJWTError` 或自定义异常，由 current_user.py 统一转 401
- ⚠️ 遗留：subject 不是数字时抛 `jwt.InvalidTokenError` → 会变成 500。当前系统签发的 token 不会触发，但要意识到这条边没闭合

### app/db.py —— 数据库连接的管家
- 为什么 get_db 用 yield + finally close：FastAPI 依赖注入的约定；yield 保证请求结束一定关连接（return 做不到）
- 为什么 autoflush=False：避免查询时偷偷发 SQL，事务边界由你自己控制
- ⚠️ `echo=True` 是开发调试用的（全量打印 SQL=性能+日志噪音），上线前必须关（M11 处理，先记着）

### app/models/user.py —— 表结构的定义
- 为什么 SQLAlchemy 2.0 的 `Mapped/mapped_column`：类型标注即列定义，可读性好、静态检查友好
- ⚠️ 字段名 `password` vs 契约的 `password_hash`：契约漂移。功能没错，但原则是"契约和实现必须一致"——二选一改掉（建议改回 password_hash，和契约、面试故事统一）

### app/schemas/user.py —— 请求/响应的守门员
- 为什么 `password max_length=72`：**bcrypt 只取前 72 字节，超长会被静默截断**——这个细节多数人不知道，面试亮点，背下来
- 为什么 UserOut 只返回 id/email：最小暴露原则，绝不把 password_hash 序列化出去

### app/api/v1/user.py —— 路由（HTTP 世界的入口）
- 为什么注册先查重再插入：能返回友好的 409 而不是数据库报错
- ⚠️ 竞态（契约预埋题，面试必问）：两个请求并发注册同一邮箱，先查后插会双双通过查重 → 正确做法：靠数据库 unique 约束兜底 + 捕获 `IntegrityError` 返回 409
- 为什么 login 统一返回"密码或邮箱错误"：不告诉攻击者"这个邮箱存在"，防用户枚举

### app/api/current_user.py —— 鉴权守卫
- 为什么用 `HTTPBearer` 而不是手写 header 解析：标准库干标准事，自动处理格式错误
- 依赖缓存：同一请求内 get_db 只执行一次，守卫和路由拿到同一个 session（你写的这条注释是对的，说明真懂了）

### tests/conftest.py —— 测试地基（这层写得最好）
- 为什么内存 SQLite + StaticPool：内存库默认每连接独立，StaticPool 让所有连接共享同一份数据
- 为什么 dependency_overrides：把生产 get_db 换成测试库，测完 clear()，互不污染
- 这是你能写出来的高级操作，面试讲这个能镇场子

## 3. 两个失败测试的根因（真实项目最常见的坑：测试污染）
pytest 按文件名排序执行：test_bcrypt → test_db → test_health → **test_jwt** → test_users
1. `test_jwt.py` 第 14 行 `settings.jwt_expire_minutes = -1` **改了全局配置且不恢复**
   → 后面 test_users 里 login 签发的 token 立刻"过期" → /me 返回 401 → `test_me_with_valid_token` 失败
2. test_jwt 自己的 `except jwt.ExpiredSignatureError` **永远捕获不到**：decode_token 已把 ExpiredSignatureError（属于 PyJWTError）转成了 HTTPException(401)
**铁证**：单独跑 `tests/test_users.py` = 8 passed；全量跑 = 2 failed
修法：
- 立刻修：test_jwt 用 try/finally 或 pytest 的 monkeypatch 恢复 settings
- 根本修：把 security.py 的 HTTPException 拆出去（见 §2），decode_token 直接抛 PyJWTError，测试断言异常类型
