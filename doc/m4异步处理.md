# 模块 M4 接口契约：异步处理与状态机

## 1. 目标
上传后立即返回 201，后台自动解析文档为全文文本，状态机 pending→processing→done/failed。
M4 只解析 .txt（PDF 抽取+切块留给 M5）。

## 2. 目录增量 + 表变更
app/services/parser.py         # ★ 纯业务函数，不碰 HTTP（M3 的教训）
documents 表 ALTER 加两列：
- text: Text, nullable            # 解析出的全文（M5 从这里切块）
- error_message: str(255), nullable

## 3. 状态机
pending → processing → done
                    ↘ failed（写 error_message）
状态只由后台任务改，路由不碰状态。

## 4. API 变更
POST /api/v1/documents          # 改回契约路径！
  响应 201 立即返回（status 还是 pending/processing，不等待解析）
GET /api/v1/documents/{id}
  响应增加 text（done 时非空）、error_message（failed 时非空）

## 5. DoD
- [ ] 上传 .txt → 201 立即返回；轮询 GET /{id} 最终 done 且 text 非空
- [ ] 上传空/坏文件 → failed + error_message 非空
- [ ] 401/415/413 行为不变
- [ ] 数据库有 text、error_message 两列
- [ ] pytest 全绿（新增 ≥4 个）
- [ ] 三问复盘写进 doc/m4异步处理.md + 合上重写 process_document

## 6. 技术约束
- 用 FastAPI BackgroundTasks，不引 Celery（为什么？→ 会考①）
- process_document 里自己开 session（不依赖路由的 get_db）
- txt 解码兜底：utf-8 → utf-8-sig → gbk（先猜再问的好题）

## 7. 会考问题
- BackgroundTasks 和 Celery 的区别？什么时候必须换？
- 进程崩溃时 BackgroundTasks 任务会怎样？生产怎么解？
- 为什么响应要先返回？长任务为什么不能卡在请求里？
- 任务失败怎么让用户知道？重试怎么做？幂等怎么保证？
