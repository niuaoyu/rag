## 三问复盘
**1. 为什么响应要先返回，长任务不能卡在请求里？**
解析 PDF + 调 embedding 是秒级到几十秒级。卡在请求里会：占满 worker（并发一上来全线排队）、
触发客户端/网关超时、客户端重试还会重复触发解析。所以先返回 201 + pending，客户端轮询。

**2. 进程崩溃时 BackgroundTasks 的任务会怎样？生产怎么解？**
直接丢：任务只存在于进程内存里，进程没了任务也没了，且**用户看到的状态会永远停在 processing**。
生产要换成有持久化队列的方案（Celery/RQ + broker），并把"任务超时未完成"作为可观测指标去报警。
另一个补丁是给 processing 加超时兜底（超过 N 分钟仍未 done → 标记 failed 允许重试）——本项目未做。

**3. 任务失败怎么让用户知道？重试怎么做？幂等怎么保证？**
- 知道：`status=failed` + `error_message`（截断到 255），客户端轮询就能看到。
- 重试：`POST /documents/{id}/reprocess` 显式重跑（不做自动重试，因为 embedding 调用失败往往是配额/网络问题，
  无脑重试会放大成本）。
- 幂等：重跑前先删该文档的旧 chunks 和旧向量，再写新的；`chunks` 表还有 `UNIQUE(document_id, ordinal)` 兜底。
  实测：重跑后块数与向量数都不变（`test_reprocess_is_idempotent`）。

## 踩坑记录（比结论更值钱）

   这类 bug 不会报错，只会让断言"莫名失败"，是最难查的一类。

   新 clone 装不上。已修。

   修好之后也不能只断言 201（文件真被写到 /etc 也会通过），改成查磁盘断言落盘名是 uuid 且没跑出 uploads。
4. **`create_all` 不会 ALTER 已有表**：不写 `upgrade_db.py` 的话，本地老库跑新代码直接 `no such column`。
