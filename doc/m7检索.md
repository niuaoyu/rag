# 模块 M7 接口契约：检索

## 1. 目标
`query → embedding → 向量库 top-k（带 user_id 过滤）→ 回表取正文 → 组装来源信息`。

## 2. 目录增量
```
app/services/retrieval.py    # search_chunks(db, user_id, query, top_k, document_ids)
```

## 3. 两层隔离（本模块最容易被追问的点）
1. **向量库层**：`Filter(must=[FieldCondition(key="user_id", ...)])` —— 检索请求本身就限定在自己数据里。
2. **关系库层**：回表时 `join(Document).filter(Document.user_id == user_id)` —— 即使 payload 被写脏也不会越权返回。

> 面试会问"你的多租户隔离做在哪一层？" 答案是"两层都做"，并说清第二层是 defense in depth，
> 不是重复劳动：向量库的过滤条件写错是**静默越权**，关系库的校验是最后一道闸。

## 4. 性能取舍
- 回表用一次 `in_` 批量查询，**不 for 循环 `db.get()`**（N+1）。
- 结果顺序保持**向量库的相似度序**，不用数据库返回顺序（数据库返回顺序无意义）。
- `min_score` 过滤在向量库侧完成，避免把低分块带进后续 prompt 白烧 token。

## 5. DoD
- [x] 检索"检索增强生成"能返回最相关块，且命中集合 ⊆ 该用户该文档的块
- [x] 用户 B 检索不到用户 A 的任何块（`test_retrieval_does_not_leak_across_users`）
- [x] 指定 `document_ids` 时校验归属，别人的 id 一律 404（`test_document_ids_of_other_user_is_404`）
- [x] `top_k` / `min_score` / `document_ids` 三个过滤条件各有单测（`tests/test_vector_store.py`）
- [x] 检索延迟可观测（`/chat/ask` 返回 `latency_ms`）

## 6. 会考问题
1. top-k 的 k 怎么定？k 变大以后，答案质量、延迟、成本分别怎么变？
2. 相似度高但内容不相关的块混进来怎么办？（→ 答 rerank / 关键词混合检索 / 阈值，并说清各自代价）
3. 检索不到内容时你的系统怎么表现？（→ `mode=no_context`，不调模型，这是防幻觉的硬约束）
4. 为什么不在检索阶段做聚合统计？（→ 向量检索不保证"数得准"，聚合必须走结构化查询）
5. 如果语料能整体塞进 1M 上下文，还要 RAG 吗？（→ 不一定；RAG 的价值在于把黑盒拆成可分别测量的三段）

## 7. 实测（2026-10-11，本沙箱）
| 项 | 值 |
| --- | --- |
| 检索延迟（服务端 `latency_ms`，含 query embedding + 向量检索 + 回表） | **2ms**（hash 档，4 个块） |
| 客户端 wall time | 5ms |
| top-3 命中示例 | 问"RAG 的检索阶段主要解决什么问题？" → `rag_notes.txt` 第 1 块 score 0.46、第 2 块 0.35、`agent_notes.txt` 第 1 块 0.30 |
| 评测器 | `scripts/eval_retrieval.py`：hit@3 = 6/6，MRR = 1.0000（**hash 档，见下方警告**） |

> ⚠️ 上面的 hit@3/MRR **不是检索质量证据**：只有 4 个块、top_k=3，且用的是 hash（词面）向量。
> 真实数字必须在 `EMBEDDING_PROVIDER=openai` 下、用**足够大的语料**（建议 100+ 文档、20+ 查询）重跑。
> 未测之前，简历和面试里**不许**出现"检索准确率 XX%"这类说法。
