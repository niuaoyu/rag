# 模块 M7 接口契约：检索

## 1. 目标
`query → embedding → 向量库 top-k（带 user_id 过滤）→ 回表取正文 → 组装来源信息`。

## 2. 目录增量
```
app/services/retrieval.py    # search_chunks(db, user_id, query, top_k, document_ids)
```

## 3. 两层隔离（本模块最容易被追问的点）
1. **向量库层**：`Filter(must=[FieldCondition(key="user_id", ...)])` —— 检索请求本身就限定在自己数据里。
2. **关系库层**：回表时 `join(Document).filter(Document.user_id == user_id)` —— 即使 payload 被写脏也不会越权返回。

> 面试会问"你的多租户隔离做在哪一层？" 答案是"两层都做"，并说清第二层是 defense in depth，
> 不是重复劳动：向量库的过滤条件写错是**静默越权**，关系库的校验是最后一道闸。

## 4. 性能取舍
- 回表用一次 `in_` 批量查询，**不 for 循环 `db.get()`**（N+1）。
- 结果顺序保持**向量库的相似度序**，不用数据库返回顺序（数据库返回顺序无意义）。
- `min_score` 过滤在向量库侧完成，避免把低分块带进后续 prompt 白烧 token。

## 5. DoD
- [x] 检索"检索增强生成"能返回最相关块，且命中集合 ⊆ 该用户该文档的块
## 7. 实测（2026-10-11，本沙箱）

评测脚本 `scripts/eval_retrieval.py`；语料 `scripts/fetch_corpus.py --source wiki`（中文维基百科导言段，**156 篇文档 / 约 800 块**）。

### 7.1 标题查询基准（40 条查询 / top_k=5）
| embedding | doc recall@5 | MRR@5 |
| --- | --- | --- |
| `hash`（词面哈希） | 92.50% | 0.7392 |
| `local`（bge-small-zh ONNX，语义） | 82.50% | 0.7758 |

**这个结果不能读成「hash 比语义模型好」**：标题查询里标题原样出现在正文，词面哈希天然占便宜，
这是基准本身的偏差。语义模型 recall 略低但 MRR 更高，说明它把正确文档排得更靠前。

### 7.2 改写查询基准（20 条，由 LLM 改写且禁止出现标题实词）
| embedding | doc recall@5 | MRR@5 |
| --- | --- | --- |
| `hash`（词面哈希） | 60.00%（12/20） | 0.4667 |
| `local`（语义） | **90.00%（18/20）** | **0.6433** |

查询与原文没有共同实词时，词面哈希掉到 60%，语义模型 90%（**+30 个百分点**，MRR +0.18）。
这才是能区分两种检索方式的基准；生成方式见 `scripts/gen_eval_queries.py`（seed 固定，可复现）。

### 7.3 延迟
| 项 | 值 | 条件 |
| --- | --- | --- |
| 检索（服务端 `latency_ms`） | 2ms（hash） | 4 块的小语料 |
| 检索 + query embedding（local） | 见 `doc/架构与决策.md` | 156 篇 / ~800 块，CPU ONNX |

> 结论只在"这个语料 + 这套参数"下成立；换语料或换模型必须重跑，不许外推。
