# 架构与决策记录（arena/mvp-0.1）

> 原则：每个"为什么这么选"都要能扛住面试官三层追问。本文记录关键决策与代价。

## 1. 总体架构

```
浏览器(Web UI) ──> FastAPI
                   ├─ /auth/*        注册/登录/JWT（bcrypt + PyJWT）
                   ├─ /documents/*   上传(202) → BackgroundTasks 后台解析
                   ├─ /chat          同步问答（检索→Agent→引用）
                   ├─ /chat/stream   SSE 流式问答（事件流）
                   └─ /health        含 llm/embedding provider 自报
                        │
     ┌──────────────────┼───────────────────────┐
     │                  │                       │
  SQLAlchemy(SQLite)  服务层                外部依赖
  users/documents/     parsing→chunking      LLM: OpenAI 兼容网关
  chunks/conversations embedding→落库        (deepseek-v41-flash, 1M ctx)
  messages             vectorstore: 余弦检索  Weather: OpenWeatherMap/离线mock
  (向量以 JSON 存库)
```

## 2. 关键决策

### D1：向量存 SQLite(JSON 列) + 进程内余弦检索，而不是 Qdrant
- **为什么**：MVP 数据量（百文档×千块）内暴力检索 P99 可忽略；省一个有状态服务，`docker compose up` 单容器全链路可跑。
- **接口不变量**：`search_chunks(db, user_id, query, top_k) -> [(Chunk, score)]` 签名稳定，换 pgvector/Qdrant 只动一个文件。
- **代价（诚实）**：全量加载用户 chunks 到内存，10万块级会慢；无 HNSW。
- **升级路径**：`EMBEDDING_PROVIDER=openai` + `vectorstore.py` 内部替换，其余零改动。

### D2：hash 嵌入做离线默认，真实 embedding 留开关
- 字符 n-gram + md5 符号哈希，离线/确定/免费，让"相似文本更近"在 demo 成立。
- 诚实声明：这是**词面向量**，语义检索质量有天花板（eval 若只测它，数字会虚高——简历不引用该 eval）。

### D3：LLM 客户端必须支持推理型网关
- 实测校园网关 `deepseek-v41-flash`：不传 `reasoning_effort` 且 `max_tokens` 小时，token 全进思考通道，**content 为空**。
- 方案：`LLM_REASONING_EFFORT`（空=不传）+ `LLM_MAX_TOKENS=0`（不传）+ 空 content 时抛带修复指引的 `LLMError`。
- 意义：同一个客户端兼容 OpenAI / DeepSeek / Qwen / vLLM，只换三个环境变量。

### D4：Agent 工具调用用"轮次预算"而不是无限循环
- `TOOL_MAX_ROUNDS=3`：每轮模型可返回 tool_calls，执行后回填 `role=tool` 消息；预算耗尽去掉 tools 强制收口。
- 防御：模型反复 tool_call 不收敛 / mock 死循环 / 恶意 prompt 让 Agent 空转，都被预算截断。
- 工具注册表：`REGISTRY = {name: (schema, fn)}`，新增工具只改一处。

### D5：SSE 流式按"阶段事件"设计，不只是 token
- 事件序列：`meta`(会话id) → `stage`(retrieving) → `citations`(先行) → [`tool_calls`]* → `delta`* → `done`。
- 为什么引用先发：检索发生在生成前，先发引用让前端能先渲染"依据"，TTFT 体感 0.70s。
- 工程细节：流式生成器**自管 SessionLocal**——请求级 `Depends(get_db)` 的 session 在响应头返回后就关了，流式期间还能用的一定要自己开。
- 首轮带 tools 流式监听 tool_calls 分片（OpenAI 的 delta.tool_calls 按 index 拼装），命中则中断本轮、执行工具、下一轮重新流式生成最终答案。

### D6：统一错误出口 `{code, message}`
- `AppError`(业务) / `HTTPException`(框架, 同时接管 starlette 的，否则 404 路由错误仍是 `{"detail"}`) / `RequestValidationError`(422) / 兜底 `Exception`(500，不泄漏内部信息)。
- 前端只写一种错误处理；`detail` 字段保留兼容旧 UI。
- 500 断言 `"boom" not in r.text`：内部异常细节只进日志不进响应。

### D7：后台任务用进程内线程 + 自管 session（暂不上 Celery）
- BackgroundTasks 足够：解析一个 PDF 秒级；状态机 `pending→processing→done/failed` 落库可查。
- 失败兜底：任务内 try/except 写 `status=failed + error`，前端可见失败原因。
- 升级路径：换 Celery/RQ 只替换 `background_tasks.add_task` 一行 + broker。

### D8：安全基线
- bcrypt 存哈希；JWT HS256 24h；资源全部按 `user_id` 过滤（检索/文档/会话三层校验属主）。
- CORS：`allow_origins=["*"]` 必须配 `allow_credentials=False`（认证走 Authorization 头非 Cookie）；两者同为 `*`+`true` 是违反规范的组合，浏览器会直接拒绝。

## 3. 实测数字（2026-10-11，服务器实测，非估算）

## 4. 已知边界（不许装看不见）
1. 检索质量受 hash 嵌入限制；接真实 embedding 前不宣称"语义检索优秀"。
2. 无压测数据（QPS/P95 未测）；SQLite 单写者，不适合多实例。
3. 流式端点业务错误以 `{"type":"error"}` 事件返回（流已 200），文档必须写明。
4. 多轮上下文取最近 6 条，超长会话的早期信息不在 prompt 里。
