# 在具体业务上搭一个 Agent 项目（可写进简历的最小闭环）

「Agent 项目」不是把框架名写进简历，而是能回答：**业务问题是什么、Agent 的决策空间在哪、边界怎么定、失败怎么收、效果怎么评。**

## 第 0 步：先有业务闭环，再有 Agent

选一个你已经能跑通的业务，最好是你正在写的项目。判断标准：

- 有真实输入（用户问题、工单、报表、文档）；
- 有可枚举的动作（查询、检索、计算、生成、写回）；
- 有可验收的结果（能不能溯源、有没有越权、失败可不可复盘）。

本项目（知识库问答服务）的闭环：**上传文档 → 解析入库 → 检索定位 → 生成回答 → 标注引用来源**。

## 五步落地

### 1. 定义任务与决策空间

写清 Agent 能做与不能做：能用哪些工具、不能写库/删数据、不能跨用户检索、超出范围要拒答。这一步的产出就是系统提示词与工具白名单。

### 2. 把已有能力工具化

每个工具三件事：给人看的 `description`、给模型看的参数 schema、给系统用的执行边界。

- 参数校验：模型给的参数不可信，必填项、枚举、`additionalProperties: false` 都要声明；
- 权限：工具在构造时就绑定当前用户，模型无法绕过（本项目 `build_document_tools(db, user_id)`）；
- 返回：统一压成一段文本观察结果并截断，避免撑爆下一轮上下文；
- 失败：工具内部异常不抛出，转成失败观察结果交给模型决策。

### 3. 编排循环

模型决策 → 调用工具 → 观察结果回灌 → 再决策，直到给出最终回答。必须同时设三个边界：

| 边界 | 为什么必须 | 本项目位置 |
| --- | --- | --- |
| 步数预算 | 防止工具失败后反复重试打满成本 | `app/agent/loop.py` `max_steps` |
| 单步调用上限 | 防止一次返回几十个调用 | `max_tool_calls_per_step` |
| 单次工具超时 | 防止一个慢工具卡住整个请求 | `app/agent/tools.py` 线程 + 事件超时 |

降级策略要分开：模型错误 → 可读提示；工具错误 → 失败观察结果继续；预算耗尽 → 返回已得结论 + 范围建议。

### 4. 观测

每次运行落一份结构化轨迹（JSONL）：逐步记录模型决策、工具名与参数摘要、耗时、错误、最终停止原因。轨迹是排障入口，也是你简历里「可观测」这条主张的唯一硬证据。

### 5. 评测

- **确定性回归**：用假模型（脚本化响应）覆盖直接回答、多步调用、工具失败、预算耗尽、模型错误五条路径；
- **小样本评测**：用真实模型跑 10—20 条问题，记录「工具选择是否正确、是否引用到文档、是否越权」，形成可复现的评测记录；
- 评测集要包含失败样本（无匹配文档、问题超范围、越权请求），只测 happy path 的评测没有说服力。

## 每步对应哪条账本证据

| 落地步骤 | 账本 `sources` 写什么 | 可写进简历的措辞方向 |
| --- | --- | --- |
| 工具化 | 工具层文件 + 参数/权限测试 | 分层工具编排、权限边界内建 |
| 编排 | 循环实现 + 五类路径测试 | 运行时预算与降级 |
| 观测 | 轨迹模块 + 轨迹样例文件 | 可观测运行轨迹、按步排障 |
| 评测 | 评测脚本 + 评测结果表 | 离线评测与回归门禁 |

## 常见坑

- **伪 Agent**：只会调一次工具，没有多步决策与失败恢复，被问两句就露。
- **没有预算**：模型重试导致成本不可控，这是面试官最爱追问的点。
- **工具里直接抛异常**：一次工具失败把整个请求打成 500。
- **没有轨迹**：线上出问题只能靠猜，简历里也拿不出证据。
- **评测只测 happy path**：无法说明边界行为。
- **把 AI 写的代码说成自己主导**：追问「为什么这么设计」时答不上来，直接暴露。

## 高频追问

1. 工具参数不可信，你怎么校验和兜底？
2. 模型反复调用同一个失败工具，你怎么止损？
3. 步数预算设多少？依据是什么？超预算返回什么？
4. 单次工具超时怎么实现？超时后那个线程怎么办？
5. 为什么不用现成编排框架？自研编排换来了什么？
6. 多租户下模型能不能拿到别人的数据？你在哪一层保证的？
7. 轨迹里记录哪些字段？为什么参数只记摘要？
8. 怎么判断一次改动没有让效果变差？
9. 真实模型下的成本与延迟你怎么测？没测过的话你打算怎么测？
10. 如果要把这个 Agent 接到工单系统，你会先改哪一层？
