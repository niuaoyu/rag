# Agent 岗简历 Bullet Few-shot（领域中立）

本文件只约束 bullet 的**形态**，不提供可复制的素材。学习顺序：先看合格 bullet 的结构，再用反例清单重写自己的句子。禁止复制本文的项目名、数字、技术名词组合。

## 使用规则

1. 先从项目事实里抽 4—6 个候选支柱（通用工程能力）。
2. 每个支柱补齐：核心矛盾、我的动作、机制、约束、结果、证据。
3. 按正例结构写一级 bullet，每条挂 `【证据：claim-xxx】`。
4. 用反例清单逐条重写。
5. 每条都要能自然导出一个「为什么这么设计 / 怎么权衡 / 怎么验证」的主问。

## 正例一：工具编排与参数边界

**项目事实（抽象）**

- 能力调用散落在多个入口，参数校验和权限判断各写一遍。
- 候选人把能力收敛成一个注册表：声明与执行放在一起。
- 模型给的参数不可信，参数错误不能让请求崩。

**合格 bullet**

> **分层工具编排：** 针对能力调用散落、校验逻辑重复的问题，把能力收敛成统一工具注册表：每项能力同时声明参数 schema 与可执行函数，校验、限时和异常收敛在工具层完成，模型参数按不可信输入处理【证据：claim-agent-001】。

**为什么合格**：先说矛盾；机制说明「怎么工作」而不是罗列框架名；结果落在可验证的架构变化上；没有内部类名。

## 正例二：预算与降级

**项目事实（抽象）**

- 多步调用可能反复重试，把时间和成本打满。
- 候选人给编排循环加了步数预算和单步调用上限。
- 模型错误和工具错误走不同降级路径。

**合格 bullet**

> **运行时预算与降级：** 针对多步调用可能反复重试、把成本打满的问题，为编排循环设置步数预算与单步调用上限，并将模型错误与工具错误分开降级：模型不可用时返回可读提示，预算耗尽时返回已得结论加范围建议【证据：claim-agent-002】。单次工具执行限时，卡死的调用不阻塞后续请求。

**为什么合格**：约束和边界写清楚了；「分开降级」是可追问的设计决策；没有编造任何延迟或成本数字。

## 正例三：把 AI 协作写成真实形态

**项目事实（抽象）**

- 候选人与 AI 结对完成实现，自己负责边界定义、测试补齐和调试。
- 有一段对话记录了错误假设被推翻的过程。

**合格 bullet**

> **可观测运行轨迹：** 针对「一次失败问答卡在哪一步说不清」的问题，为每次运行落地结构化轨迹：逐步记录模型决策、工具调用参数摘要、耗时与错误，使排障从看日志猜变成按步定位【待补：补一次真实模型运行的轨迹样例】。

**为什么合格**：写的是机制与用途，没有把 AI 的产出说成自己的独立成果；未验证的部分用 `【待补】` 标出，而不是编一个数字。

## 反例

```text
- 接入 LangChain 搭建 RAG 问答链路，性能提升 300%，稳定性大幅提升。
- 使用工具调用和向量检索，实现 Agent 自动决策。
- 熟悉大模型应用开发，有丰富的 Agent 项目经验。
```

**失败原因**

- 框架名代替了机制：面试官只能问「LangChain 怎么用的」，你答不出设计取舍。
- 数字没有口径，且量级夸张，第一眼就像编的。
- 「自动决策」没有说明决策空间、失败处理和边界。
- 「熟悉 / 丰富经验」是自评，不是事实。

## 改写对照

**原始描述**：用 LangChain 做了个问答 Agent，效果不错。

**合格改写**：**编排与边界治理：** 针对问答链路里工具调用不可控的问题，把编排收成有限步循环：模型每步只允许在已注册工具内选择，单步调用数有上限，工具异常转成失败观察结果回灌模型，模型不可用与预算耗尽分别降级；覆盖上述路径的测试用例共 N 条【证据：claim-agent-002】。

## 生成后硬检查

- [ ] 一级 bullet 以 `**通用支柱名：**` 开头，支柱名是面试官可理解的工程能力。
- [ ] 每条只表达一个支柱，不是功能清单。
- [ ] 至少含「问题或演进 + 机制 + 结果」，关键条补约束或边界。
- [ ] 结果紧跟机制，能回答「用了它系统发生了什么变化」。
- [ ] 没有指标就写架构结果或测量计划，不用「提升性能 / 提高稳定性 / 优化体验」。
- [ ] 指标来自账本 `sources`，口径写清；无实测标「待测」。
- [ ] 内部符号下沉到源码证据索引。
- [ ] 职责动词与账本 `responsibility_level` 一致。
- [ ] 没有复制本文档或别人简历的项目名、数字、领域名词。
