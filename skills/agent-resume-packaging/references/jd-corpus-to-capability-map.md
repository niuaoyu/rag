# 把 JD 语料变成「先验知识」而不是「上下文垃圾」

目标：让 AI 知道**这个岗位会怎么问、用什么词**，同时不让它把 JD 里的要求当成你做过的事。

## 为什么直接把一堆 JD/简历/面经塞给模型会失败

1. **层次混淆**：模型分不清「JD 要求」和「候选人事实」，于是把 JD 里的技术栈和指标写进你的经历。
2. **长上下文稀释**：几十份 JD 进去，模型只记得最近几条和你反复强调的那几条，输出变成关键词拼贴。
3. **没有裁决标准**：没有账本时，模型无法判断一句话能不能写，只能选「听起来更厉害」的版本——这正是你自己看着假的原因。
4. **不可复用**：每次都要重喂，且无法回归测试；换个岗位就得从头再来。

## 两阶段做法

### 阶段一（离线，做一次）：JD → 能力词典

把 20—50 份目标岗位 JD 解析成结构化条目，聚合成一份 `capability-map.json`：

```json
{
  "role": "Agent 开发工程师",
  "capabilities": [
    {
      "capability": "工具调用与编排",
      "jd_terms": ["function calling", "tool use", "工作流编排", "多步推理"],
      "jd_frequency": 0.82,
      "resume_pillars": ["分层工具编排", "运行时预算与降级"],
      "evidence_needed": ["工具 schema 与执行边界代码", "步数/超时/错误降级测试"],
      "interview_questions": [
        "工具参数不可信时你怎么校验？",
        "模型反复调用同一个失败工具怎么办？"
      ]
    }
  ]
}
```

解析时只保留四类信息：**职责动词**（设计/落地/优化/接入）、**能力名词**（编排、检索、评测、降级）、**约束条件**（并发、成本、时延、权限）、**加分项**（某框架、某领域经验）。公司宣传语、福利、价值观不要进词典。

### 阶段二（每次生成时）：按目标 JD 注入 top-N

给模型的输入固定为四块，缺一块就停：

1. **事实层**：`ledger.json` 全文（这是唯一的事实来源）。
2. **领域层**：从 `capability-map.json` 挑与目标 JD 最相关的 5—8 条能力（不是全部）。
3. **结构层**：few-shot 文件（只学结构）。
4. **输出约束**：每条挂 `【证据：claim-xxx】`；没有证据写 `【待补：...】`；禁止出现未在账本中的数字与框架名。

注入模板（可直接复用）：

```text
你是 Agent 岗简历包装助手。事实只能来自下面的账本，账本之外的内容一律不得写入。
任务：把账本里状态为「已确认」的主张，按目标岗位能力顺序组织成 4—6 条 bullet。

目标岗位能力（按 JD 频率排序，仅用于选词与排序，不得当作事实）：
{{top_n_capabilities}}

表达结构参考：{{few_shot_path}}（只学结构，禁止复制其中的项目名、数字、领域名词）

硬性要求：
- 每条 bullet 以 **通用支柱名：** 开头，一条只讲一个支柱；
- 每条结构为「问题或演进 → 机制 → 约束/边界 → 结果」，结果必须是可验证的架构变化或测试事实；
- 每个数字后必须紧跟【证据：claim-xxx】并写明口径，没有实测就写「待测」；
- 账本里没有的能力、框架、指标一律不写；
- 结尾附「待补清单」：为了投这个岗位，还缺哪些证据。

账本：{{ledger_json}}
```

## 反模式清单

- ❌ 把 50 份 JD 一次性丢进上下文，然后要求「综合出最好的简历」。
- ❌ 把 JD 关键词直接写进技能栏（例如没用过某编排框架却写「熟悉」）。
- ❌ 把面经答案改写成自己的经历。
- ❌ 用别人的简历当模板并顺手抄了它的数字与项目名。
- ❌ 生成完就投，不做证据回指审计。

## 迭代闭环

审计报告 → 追问模拟 → **回到账本补证据**（改代码、补测试、跑一次真实评测）→ 再生成。
只改措辞不改证据，是包装失效的根因：面试官追问两层就会露底。
